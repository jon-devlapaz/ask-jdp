## Problem statement
Employers who visit the live Ask JDP site can encounter the Ask UI under an invented deep link rather than an explicit unknown-route state, potentially seeing a prior chat while the invalid URL remains in the address bar. Repository evidence identifies an unrestricted client-index fallback in the Node app and an HTML GET/HEAD index retry in the Sites worker. These are demonstrated routing gaps, not evidence of the current live deployment. The original reproduction at https://ask-jdp.marten-pollux.ts.net/ remains unverified until retested.

## Proposed outcome
Unsupported paths, including `/foo`, `/chat`, and `/ask/xyz`, display an explicit unknown-route state with a usable return to `/`, without silently reopening an existing conversation as though the URL were valid. Preserve `/`, supported assets, and existing API behavior, including through direct loads, reload, and browser Back/Forward. Cover the deployed serving path and both serving paths where applicable. HTTP 404 is permitted, not an additional requirement. A standalone unknown-route document, an explicit client-rendered state, or a combination can satisfy this boundary; implementation selection remains downstream work.
